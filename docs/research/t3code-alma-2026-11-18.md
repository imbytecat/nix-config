# T3 Code 与 Alma 调研：对照现有 harness（2026-11-18）

## 结论

**不换。** herdr-app + herdr-core 承载原生 TUI 的 `omp` / Codex / `dsh`，全部配置由 Nix 声明；这个组合仍最贴合 [11-15 调研](orca-alternatives-2026-11-15.md)记录的用法。两款工具都不构成替代：

- **T3 Code**：11-15 的判断不变。`omp` 只能经 `omp acp` 变成聊天线程；原生 Pi RPC 驱动明确不支持 `omp`（[#19490](https://github.com/pingdotgg/t3code/issues/19490)，closed not_planned），上游还关掉了两个外部 `omp` provider PR。原生 TUI 状态检测的请求同样 not_planned（[#37671](https://github.com/pingdotgg/t3code/issues/37671)）。遥测仍默认开启，11-15 记下的三个 Wayland issue 仍 open。唯一改善是 Codex 手动模式配自定义网关更顺。
- **Alma**：唯一能挂到现有 herdr-core、与 herdr-app 并存的 GUI。它只读 `~/.omp/agent/sessions` 与 Codex rollout 来渲染聊天视图，`omp` 仍以原生 TUI 跑在 core 里，并补上 herdr-app 缺的系统通知。但它闭源，内置 PostHog（开关以 opt-out 引入），自更新关不掉（30 天约 470 个桌面版），会改写 herdr-app 存在 core 里的布局 doc，还可能自启或安装上游 `herdr-core`；这些与本仓约束正面冲突。`dsh` 不支持，也不能从 Alma 新建 `omp`。
- **Alma 自带 harness**：FrontierHarness v1.1 中与 `omp` 在误差内打平，每次通过贵约 24%，且只测了开源模型；不构成换主力 harness 的理由。

剩下的真实缺口仍是 herdr-app 没有系统通知（[#120](https://github.com/herdrdev/herdr-app/issues/120)，2026-11-18 仍 open）。它真影响使用时，可在 Mac 上手动试 Alma 作旁路通知器（条件见下文 Alma 的“对本仓的适配判断”），不写进 Nix 配置；否则继续等 herdr-app。

### 2. Pi provider 与 `omp`

**更正基线**：Pi provider 不是新增的。v0.1.9 已有 [`docs/user/providers-pi.md`](https://github.com/pingdotgg/t3code/blob/v0.1.9/docs/user/providers-pi.md)，11-15 文档漏记。

**协议**：Pi provider 是原生 Pi RPC 驱动，与 ACP 分开。

- 启动命令是 `<binaryPath|pi> --mode rpc [--session <file>|--no-session] --extension <T3 extension>`（`T3@main/packages/provider-pi/src/server/mcpInjection.ts` 第 249–293 行）。
- 设置项说明写的是 “Additional CLI arguments passed to pi --mode rpc”（`T3@main/packages/provider-pi/src/settings.ts` 第 24 行起）。
- 会话恢复、回滚、fork 使用 Pi 原生 session 文件。T3 拒绝 `--mode`、`--session` 等改变执行模式或选择会话的参数（[providers-pi.md](https://github.com/pingdotgg/t3code/blob/d0a754daeaa972101881befe74a6f99e24e25da7/docs/user/providers-pi.md)）。
- 最低版本是 Pi 0.84.3（`T3@main/packages/provider-pi/src/server/status.ts` 第 65 行）。按 semver，`omp` 18.x 能通过版本检查 `[INFERENCE]`。

**能否用 `binaryPath` 驱动 `omp`：不能，上游也不支持。**

- [#19490](https://github.com/pingdotgg/t3code/issues/19490)（2026-10-14，closed not_planned）：指向 `omp` 后 turn 永不结束。原因是 `omp` 发 `session_settled`，Pi 驱动只认 `agent_settled`。
- 维护者答复：“Oh My Pi (`omp`) is not a supported T3 Code provider … Pointing the Pi provider's `binaryPath` at `omp` is an unsupported swap”。
- 当前 `omp` 仍只发 `session_settled`（`OMP@packages/coding-agent/src/modes/rpc/rpc-session-settle.ts` 第 40 行；`modes/rpc` 中没有 `agent_settled`）。
- 同 issue 下第三方列出另外 5 处协议差异，并给出用户态 shim [`omp-t3`](https://github.com/hashangit/omp-t3)。它非官方，未核实。
- 原生 `omp` provider PR [#33065](https://github.com/pingdotgg/t3code/pull/33065)（11-12）被关闭，理由是 “We are not taking new providers from outside PRs”。
- “Oh My Pi 一键本地 ACP preset” PR [#35892](https://github.com/pingdotgg/t3code/pull/35892)（11-15）也被关闭，理由是 “not something the project wants to take on”。
- 因此 `omp` 唯一受支持的接法仍是 ACP Local command `omp acp`。

**目录与配置**

- T3 不传 `--session-dir`。session 文件由被启动的二进制按自己的 agent dir 写入。对官方 Pi，T3 的 usage 与 session import 读 `PI_CODING_AGENT_DIR` 或 `~/.pi/agent/sessions`（`T3@main/packages/provider-pi/src/server/usage.ts` 第 182–185 行；[#34726](https://github.com/pingdotgg/t3code/pull/34726)）。
- `omp` 的 agent dir 是 `~/.omp/agent`（`OMP@packages/coding-agent/src/config/config-file.ts` 第 152 行、`model-registry.ts` 第 783 行）。如果硬接 `omp`，T3 的 usage/import 会读错目录 `[INFERENCE]`。
- T3 写入的 extension 文件 `pi-t3-mcp-extension.ts` 放在 T3 home 的 `caches/` 下（`T3@main/packages/provider-pi/src/server/adapter.ts` 第 507 行；`T3@main/apps/server/src/config.ts` 第 155 行），不写 `~/.pi` 或 `~/.omp`。

**只读 `~/.omp/agent/*.yml`**

- ACP 路径上 T3 切模型时，`omp` 调用 `session.setModel(model)`，不带 `persist`（`OMP@packages/coding-agent/src/modes/acp/acp-agent.ts` 第 2519 行）。只有 `persist` 为真才写 settings（`OMP@packages/coding-agent/src/session/model-controls.ts` 第 335 行）。所以切模型不写 `config.yml`。
- 其他 ACP 操作（thinking、mode）是否写盘未核实。

**11-10 之后的 `omp` 相关 issue/PR**

- [#36984](https://github.com/pingdotgg/t3code/issues/36984)：已由 [#36997](https://github.com/pingdotgg/t3code/pull/36997) 修复，含于 v0.1.10。
- [#35892](https://github.com/pingdotgg/t3code/pull/35892) 与 [#33065](https://github.com/pingdotgg/t3code/pull/33065)：关闭。
- [#32322](https://github.com/pingdotgg/t3code/issues/32322) / [#32321](https://github.com/pingdotgg/t3code/pull/32321)：针对 OmO（另一个 Pi fork），不涉及 `omp`。

**自定义 `model_provider`**

- T3 读取 `config/read` 判断路由。只有 base_url 为 `api.openai.com` 或 `chatgpt.com` 才视为原生 OpenAI 并查询配额（`T3@main/apps/server/src/provider/CodexProvider.ts` 第 76–137 行）。

### 7. 遥测

**默认开启**：`Config.Boolean("T3CODE_TELEMETRY_ENABLED")` 的默认值是 `true`（`T3@main/apps/server/src/telemetry/AnalyticsService.ts` 第 74 行）。`telemetry.md` 与 `managed-policy.md` 从 v0.1.9 到 main 无 diff。

**关闭方法**

- server 端：`T3CODE_TELEMETRY_ENABLED=false`。它同时关闭发往 `ingest.t3.codes`、再转 PostHog 的产品事件，以及发往 Axiom 的 relay trace。
- 设 `T3CODE_OTEL_SDK_DISABLED` 或 `OTEL_SDK_DISABLED` 也会停 relay trace。
- 桌面端在 macOS/Linux 从 login shell profile 读取该变量。
- managed policy 写 `"limits": { "telemetry": false }`。文件路径：macOS 为 `/Library/Application Support/T3Code/policy.json`（或 `com.t3tools.t3code` 配置描述文件），Linux 为 `/etc/t3code/policy.json`（[managed-policy.md](https://github.com/pingdotgg/t3code/blob/d0a754daeaa972101881befe74a6f99e24e25da7/docs/user/managed-policy.md) 第 51–53、253 行）。11-15 文档只写了 Linux 路径。

**关不掉的部分**：浏览器 web client 与手机 app 的 relay trace；手机崩溃报告只能在 app 内关；“Publish agent activity” 不受上述开关控制。

### 3. herdr GUI 客户端

**结论：Alma 同时支持 herdr TUI server 和 herdr-core/`hc`，两者可以并存。** 文档只写了 TUI 的 socket，代码中已经包含 herdr-core 客户端。

- **两个后端**：[R@v0.4.245](https://github.com/yetone/alma-releases/releases/tag/v0.4.245)（2026-10-29）写明 “Added support for the new Herdr.app (herdr-core) alongside the existing Herdr”。`server.mjs` 中有两个 client，由 hub 合并结果（静态检查）：
  - TUI client 使用 JSON-lines 协议，消息 id 为 `alma:N`，调用 `pane.read`、`pane.process_info` 等方法；
  - core client 使用 JSON-RPC 2.0，调用 `terminal.get/list/read/run/send/kill`、`doc.get/set`、`machine.exec`、`hello` 等方法。

  yetone 在 herdrdev 中自称 “Alma (a herdr-core client)”（[herdr-core#70](https://github.com/herdrdev/herdr-core/issues/70)）；[herdr#5895](https://github.com/herdrdev/herdr/issues/5895)（2026-11-08）讨论的则是 TUI 路径（`pane.read`，herdr 0.9.1 protocol 22）。
- **socket 发现**：
  - TUI：依次查 `HERDR_SOCKET_PATH`、`HERDR_SOCKET`、`<config>/herdr/sessions/<HERDR_SESSION>/herdr.sock`、`<config>/herdr/herdr.sock`（[文档](https://alma.now/docs/features/herdr)，代码一致）。
  - herdr-core：依次查 `HC_SOCKET`、`~/.config/herdr-core/config.toml` 中的 `socket =`、`$XDG_RUNTIME_DIR` 或 `$XDG_STATE_HOME` 下的 `herdr-core/<session>.sock` 与 `herdr-core/<session>/<session>.sock`（session 取 `HC_SESSION`，默认 `default`）、`~/.local/state/herdr-core/default/default.sock`，最后扫描目录。Windows 使用 `\\.\pipe\herdr-core-<user>-<session>.sock`。
  - 环境变量来源：Alma 用 `$SHELL -ilc` 读取登录 shell 中的上述变量（静态检查）。Linux 上 `<session>.sock` 漏查的问题 [#211](https://github.com/yetone/alma-releases/issues/211) 仍 open，但 0.4.782 代码已同时查两种路径 `[INFERENCE: 已修未关单]`。相关修复见 [R@v0.4.259](https://github.com/yetone/alma-releases/releases/tag/v0.4.259)：支持任意 session 名和 `config.toml` 中的 socket。
- **最低版本**：代码中没有 herdr 或 herdr-core 的版本或协议门槛，能力按 core 的 `hello` features 探测（静态检查）。已知可用组合有 herdr 0.9.1 protocol 22（[herdr#5895](https://github.com/herdrdev/herdr/issues/5895)）、hc 0.1.16–0.1.21（[herdr-core#70](https://github.com/herdrdev/herdr-core/issues/70)、[#517](https://github.com/yetone/alma-releases/issues/517)）。
- **与 herdr-app 同时连接同一个 core**：
  - herdr-core 定位为无界面、多客户端服务：“Core draws nothing. Use it from your shell, an agent, or your own app”（[README](https://github.com/herdrdev/herdr-core/blob/c7517808d64f06609e4ecf0db1757005373cc3a3/README.md)）。
  - Alma 显式按共存设计：通过 `$HERDR_APP_HOME` 或 `~/.config/herdr-app/herdr-app.sock` 检测 herdr-app 是否在运行，并读取 `~/.config/herdr-app/view.json` 获取 herdr-app 当前可见的终端。工作区与 tab 布局读写 core 中名为 **`herdr-app` 的共享 doc**，`doc.set` 携带 version 做 CAS，冲突后重试；新建 shell 时，若 herdr-app 在运行就不改布局。终端打上 `herdr.space`、`herdr.tab`、`alma.session` 标签（静态检查）。
  - 因此同时使用受支持，但 Alma **会改写 herdr-app 的布局 doc**，包括新建、重命名、重排和关闭 tab `[INFERENCE]`。这个 doc 存在 core 状态里，不在 `~/.config/herdr*` 文件中。
- **pane 如何显示为聊天**：Alma 读取 agent 自己的会话文件，不解析屏幕，也不读 OSC 7501。
  - Codex：只读打开 `$CODEX_HOME`（默认 `~/.codex`）下的 `state_*.sqlite`，并读取 `~/.codex/sessions/**/rollout-*.jsonl`。
  - pi 与 `omp`：读取 `~/.pi/agent/sessions` 和 `~/.omp/agent/sessions/<cwd 编码>/*.jsonl`；`omp` 按 pi 格式解析。
  - Claude：读取 `$CLAUDE_CONFIG_DIR` 或 `~/.claude/projects/*/<id>.jsonl` 与 `~/.claude/sessions/<pid>.json`。
  - 会话 id 来自 core snapshot 的 `agent_session`，或按 cwd 与进程启动时间匹配。状态使用 hc 的 `status`；hc 没有报告状态时，Alma 用自己的推断补足（[R@v0.4.372](https://github.com/yetone/alma-releases/releases/tag/v0.4.372)）。yetone 也确认 “Alma reads those files to show the chat”（[herdr-core#86 评论](https://github.com/herdrdev/herdr-core/issues/86)）。
  - “screen” 视图显示真实终端：TUI 路径轮询 `pane.read` ANSI（[herdr#5895](https://github.com/herdrdev/herdr/issues/5895)），core 路径使用 `terminal.read`。闲置时约每秒一次 RPC 轮询（[#257](https://github.com/yetone/alma-releases/issues/257)）。

- **是否写入 agent 或 herdr 配置**：在 `server.mjs` 中检索 `hooks.json`、`agent/extensions`、`config.toml`、`.dsh`、`notify` 等写入点：对 `~/.codex`、`~/.omp` 只发现读取；`config.toml` 只读取 `~/.config/herdr-core/config.toml` 中的 `socket`；`hooks.json` 只用于 Alma 自己的 `~/.config/alma/hooks.json`；没有任何 `.dsh` 引用（静态检查）。需要注意的副作用：
  - Agents 页有 **Install Herdr Core** 按钮，执行 `releases.herdr.dev/core/install.sh`，安装到 `~/.local/bin` 或 `$HC_INSTALL_DIR`（[R@v0.4.525](https://github.com/yetone/alma-releases/releases/tag/v0.4.525)；静态检查），会绕开 Nix 管理的 `herdr-core`。
  - core 不在线、但能在 PATH 或 Homebrew 路径找到 `herdr-core` 时，Alma 会**自动启动 core**，除非设置 `ALMA_HERDR_AUTOSTART=0`（静态检查）。由 Alma 启动的 core 会继承 Alma 的环境（[herdr-core#86](https://github.com/herdrdev/herdr-core/issues/86)，open）`[INFERENCE]`。
- **远程 herdr-core**（例如 awesome-pc）有两条路：
  1. 本机 hc 通过 SSH `machine` 连接远端。Alma 用 core 的 `machine.exec` 在远端执行 shell 脚本，find 或 stat 会话文件，并镜像到本地 `dataDir/machines`（静态检查）。远端会话可见，但都混在 “This Mac” 下，没有机器分组（[#517](https://github.com/yetone/alma-releases/issues/517)，open）。
  2. 在远端也装 Alma，然后用 **Add computer…** 配对：优先局域网直连，否则走 E2E relay（[文档](https://alma.now/docs/features/herdr)）。Tailscale 地址是否算 “local network” 未核实。
- **herdrdev 侧**：herdr、herdr-core、herdr-app 的代码、文档和官网都没有提到 Alma；herdr-core CHANGELOG 中唯一的 “Alma” 是 AlmaLinux（[CHANGELOG](https://github.com/herdrdev/herdr-core/blob/c7517808d64f06609e4ecf0db1757005373cc3a3/CHANGELOG.md)）。yetone 以用户身份提过的 issue 有 [herdr#5895](https://github.com/herdrdev/herdr/issues/5895)（closed）、[herdr-core#70](https://github.com/herdrdev/herdr-core/issues/70)（core 0.1.21 修复）、[herdr-core#86](https://github.com/herdrdev/herdr-core/issues/86)（open）。

### 4. 通知、推送与 relay

- **桌面通知**：agent 需要用户或已完成时发系统通知，可按 workspace 或 tab 静音（[文档](https://alma.now/docs/features/herdr)）。macOS 使用 `UNUserNotificationCenter`；Linux 使用 D-Bus `org.freedesktop.Notifications`，托盘使用 ayatana-appindicator（静态检查）。这补上了 herdr-app 缺系统通知的空白（[herdr-app#120](https://github.com/herdrdev/herdr-app/issues/120)）。
- **手机推送**：电脑上的 `alma-server` 构造 APNs 或 FCM payload，以 `{t:"push", notifications:[{token, payload}]}` 发给 relay，由 relay 持有 APNs key 并转发。payload 为明文 `aps.alert.title/body`（body 截断到上限）、`thread-id`、`alma.kind/threadId/mac`，**不在 E2E 信道内**（静态检查）。relay 运营方以及 Apple、Google 能看到通知标题和正文，正文可能包含 agent 提问摘要 `[INFERENCE]`。
- **relay**：主 relay `https://relay.alma.now`，后备 `https://alma-relay.yetoneful.workers.dev`（Cloudflare Workers），由作者运营（静态检查）。协议 `alma-relay-e2e/v1`：ECDH P-256 + SHA-256 派生，AES-GCM 加密，双向独立密钥并带 confirm 步骤（静态检查）；官方说法是 “end-to-end encrypted over Alma's relay, or direct on the same Wi-Fi”（[官网](https://alma.now/)、[installation](https://alma.now/docs/guide/installation)）。配对用 pairing code 或链接，未见账号要求。手机必须经过电脑上的 Alma，不能单独连 herdr-core。

### 5. Alma 自带 agent 与聊天

- **自定义 provider**：provider 有 `api_format` 字段，枚举值为 `openai-chat`、`openai-responses`、`anthropic`，可配合自定义 Base URL、API Key 和手动填写的 model ID（静态检查 DB schema；[custom 文档](https://alma.now/docs/providers/custom)：“Manually add your model IDs”）。Anthropic provider 的 Base URL 可改为代理地址（[anthropic 文档](https://alma.now/docs/providers/anthropic)）。设置 UI 的选项是 “Anthropic Messages (/v1/messages)”、“OpenAI Responses”、“Chat Completions”（静态检查）。furtherverse 网关的三种 wire 格式都能配置 `[INFERENCE: 未实测；Anthropic 默认 base 带 /v1，需按 UI 提示填写]`。
- **Claude Code / Codex / pi 在 herdr 之外运行**：使用 **ACP**，基于 `@mcpc-tech/acp-ai-provider`（[R@v0.0.651](https://github.com/yetone/alma-releases/releases/tag/v0.0.651)）。识别的命令包括 `codex-acp`（`@zed-industries/codex-acp`）、`claude-agent-acp` / `claude-code-acp` / `acp-extension-claude`、`pi-acp`；npx 可作为后备启动方式（[R@v0.0.848](https://github.com/yetone/alma-releases/releases/tag/v0.0.848)；静态检查）。不使用 PTY。Codex 不走 Alma 自己的 `codex app-server` 驱动；只在 herdr 场景下兼容 Codex 的共享 app-server daemon（[R@v0.4.428](https://github.com/yetone/alma-releases/releases/tag/v0.4.428)）。
- **`CODEX_HOME` 与 Codex 配置**：代码中 `CODEX_HOME` 只被读取，没有被设置。codex-acp 鉴权：指定了 Alma provider 时注入 `OPENAI_API_KEY` 与 `OPENAI_BASE_URL`；否则只读 `~/.codex/auth.json` 中的 `OPENAI_API_KEY` 或 `CODEX_API_KEY` 并注入环境变量（静态检查）。因此 Alma 不改 `CODEX_HOME`，也不写 `config.toml` `[INFERENCE: 基于检索，未运行]`。codex-acp 会读取 `~/.codex/config.toml` 中的 `model_provider`，它与注入的 `OPENAI_BASE_URL` 谁优先未核实。

### 对本仓的适配判断

**不用 Alma 替换 herdr-app。它可以在 macOS 上作可选的旁路查看器，补系统通知和 `omp` 聊天视图，但前提很多。**

正面：

- 目前唯一能接入现有 herdr-core 0.1.21、与 herdr-app 并存的 GUI。
- 读 `~/.omp/agent/sessions` 和 Codex rollout 都是只读，不往 `~/.omp`、`~/.codex`、`~/.dsh` 注入 hook，也不改 `CODEX_HOME`。
- 补上 herdr-app 缺的系统通知，并可随时切回真实终端，`omp` 仍以原生 TUI 跑在 core 里。

反面（与本仓约束直接冲突）：

1. 闭源、unfree，没有隐私政策；PostHog 很可能默认开启，需要手动关闭。
2. 自更新无法完全关闭；cask 设置了 `auto_updates`，日均约 16 个版本；nixpkgs 和 llm-agents 都没有包，NUR 只有 Linux 且落后 200 多个版本。
3. 会改写 herdr-app 的布局 doc；可能自动启动或安装上游 `herdr-core`，绕开 Nix 版本。
4. 不支持 `dsh`；不能从 Alma 新建 `omp`；远程机器混排。
5. 手机推送正文以明文经过 Alma relay 和 Apple；现有 herdr 手机端走 SSH + Tailscale，不经过第三方。
6. KDE Wayland 下有标题栏和 GTK 崩溃问题，fcitx5 未经验证；455 个 open issue 对 51 个 closed，稳定性信号偏弱。

若试用，只在 Mac 上用 release zip 手动装（不要 `brew install --cask alma`：`homebrew.onActivation.cleanup = "zap"` 会在下次 switch 卸掉未声明的 cask），并且：

- 设置 `ALMA_HERDR_AUTOSTART=0`；
- 首次同步前关闭 analytics 和 Auto download updates；
- 不点 Install Herdr Core；
- 不启用手机 relay 推送。

### 未能核实

- 设置 `ALMA_UPDATE_URL` 或删除 `app-update.yml` 后，更新器是否真正停用。
- Alma 修改 `herdr-app` 布局 doc 时，herdr-app 0.1.16 能否正确合并，会不会冲突或丢 tab（未运行）。

- “Add computer…” 走 Tailscale IP 时算直连还是 relay。
- relay（relay.alma.now / Workers）的服务端代码与日志策略；推送 body 是否包含 agent 提问全文。
- codex-acp 路径下，HM 中的 `model_provider = "furtherverse"` 与 Alma 注入的 `OPENAI_BASE_URL` 谁优先。

- 0.4.782 的 Windows 与 x64 产物没有检查，只检查了 mac-arm64 zip 与 linux-amd64 deb。

## Alma 作为 harness：FrontierHarness v1.1

Alma 近期的热度主要来自 Runta 的 [FrontierHarness Eval v1.1](https://runta.com/blog/introducing-frontierharness-eval-v1-1/)（2026-11-17）：22 个 harness 配置 × 5 个开源模型 × 62 个任务 × 4 次，共 27 280 次 trial。下表由 `https://frontierharness.org/api/live` 的全部 trial 重算（剔除 infra 失败，`lookup` 记 0）；总体通过率与 [README @ `660291ec`](https://github.com/frontier-harness-eval/eval/blob/660291ecc8961a7c818996602adf8c6f2842c577/README.md) 逐项一致。

| Harness（评测版本） | 总体通过率 | 总体 $/pass | DeepSeek V4.1 Flash | Kimi-K3 |
|---|---:|---:|---:|---:|
| Codex CLI 0.164.0 | 61.1% | $0.937 | 67.3% | 63.7% |
| Alma 0.4.212 | 59.7% | $1.22 | 62.5% | 64.1% |
| Oh My Pi 18.12.6 | 57.3% | $0.983 | 57.7% | 57.7% |
| DSH Minimal 0.2.1-rc.3 | 57.4% | $1.15 | 63.7% | 59.3% |
| DSH Creator 0.2.1-rc.3 | 56.1% | $1.27 | 64.9% | 57.7% |

读法：

- 作者给的 95% 区间约 ±10 个百分点，原话 “a gap of a few points is a tie”；Kimi-K3 上 “Alma 优于 Oh My Pi” 的 best-value 结论在 4 000 次重抽样中只有 25% 成立（[blog](https://runta.com/blog/introducing-frontierharness-eval-v1-1/)）。
- 只测了 Baseten 上的开源模型，闭源模型（Claude Opus 5.5、GPT-6 Astra）是作者的下一步；本仓主力 `omp` 跑 Claude Opus 5.5、Codex 跑 GPT-6.1 Sol，都不在样本内。
- 每个 harness 用默认设置；本仓 `omp` 带 ponytail extension 与 caveman rule，不是默认形态。
- Alma 用私有源码包 `jobs/alma-source-0.4.212.tar.gz` 运行，评测仓库不含该包；形态是 `node bin/server.mjs` 后端加 `alma run --model …` CLI，启动时读取 models.dev（[suite `agents.13` @ `660291ec`](https://github.com/frontier-harness-eval/eval/blob/660291ecc8961a7c818996602adf8c6f2842c577/suites/baseten-eval.json)）。

判断：Alma 自带 harness 与 `omp` 在误差内打平，每次通过贵约 24%，不构成换主力 harness 的理由。DSH 四个 profile 在 DeepSeek 上比 `omp` 高 4–7 个点，与本仓用 `dsh` 跑 DeepSeek 的分工一致，但同样在误差内。

## 方法
